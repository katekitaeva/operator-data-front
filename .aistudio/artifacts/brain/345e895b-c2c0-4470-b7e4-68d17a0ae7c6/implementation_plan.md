# Доработка шага 5 «Запись кейса» и совместимость с архивом кейсов

Реализация финального этапа сохранения кейсов, перенос блока matching на шаг 4, полная сериализация состояния всех шагов (включая сортировки и действия) в `inbox/cases/`, совместимость со скриптом `process_cases.py` и двусторонняя обратная совместимость загрузчика кейсов.

> [!IMPORTANT]
> **Подтверждённые решения:**
> - **Формат блока сопоставления в JSON**: сохраняется как структурированный JSON-объект `matching: { problemType, blockers, fault, demand, resolution, stage, essence }` и `dictionaryVersion`.
> - **Загрузка кейсов старого формата (без `actions`)**: создаются базовые действия шага 4 с переносом текста ответа из `outcome.reply` в действие «Чат» и структурированного комментария из `outcome.comment` в действие «Закрыть тикет».

## 2. Пользовательский сценарий (UX Flows)

### Flow 1: Проверка и запись нового кейса на шаге 5
1. Оператор завершает работу на шаге 4 (согласованные действия и блок matching заполнены) и нажимает «Далее: Запись кейса».
2. На шаге 5:
   - Блок `case-summary` удалён из формы (он больше не дублирует шаг 4).
   - Оператор вводит «Ёмкий заголовок кейса», при необходимости заполняет «Что сработало» и «Комментарии QC».
   - В блоке «Предпросмотр карточки кейса» выводится полная сводка: идентификаторы, темы, проблема, требование, вердикт, чек-лист действий с их статусами, а также блок «Сопоставление кейсов (matching)» со структурированными ключами.
3. При нажатии «Записать кейс в operator-data»:
   - Формируется JSON со всеми полями, сортировками тем и действий, структурированным matching.
   - Файл сохраняется в `inbox/cases/<дата>_<тикет>.json` через GitHub API.

### Flow 2: Миграция старых кейсов («открыть -> доработать -> сохранить»)
1. Оператор нажимает внизу «Загрузить сохранённый кейс» и выбирает старый кейс (например, `2026-10-07_753683844.json`).
2. Загрузчик определяет старый формат:
   - Корректно восстанавливает данные шагов 1, 2, 3 и 5.
   - Для шага 4: генерирует стандартный набор действий, при этом автоматически заполняет текст ответа клиенту в карточке «Чат» из `outcome.reply`, а структурированный комментарий — в карточке «Закрыть тикет» из `outcome.comment`.
   - Включает режим обновления (`state.loadedCase`).
3. Оператор переходит по шагам, правит или формирует matching на шаге 4, переходит на шаг 5 и нажимает «Обновить кейс в operator-data».
4. Кейс сохраняется в `inbox/cases/` уже в новом формате со всеми новыми атрибутами.
5. Скрипт `process_cases.py` обрабатывает файл, переносит в `cases/` и обновляет манифест.

## 3. Технические изменения

### 3.1. Разметка `index.html` (Шаг 5)
- Удаление поля `<label for="case-summary">` из формы шага 5.

### 3.2. Сборка карточки и санитизация (`js/cases.js`)
- Обновление функции `buildCaseCard()`:
  - Формирование структурированного объекта `matching`:
    ```json
    "matching": {
      "problemType": "...",
      "blockers": "...",
      "fault": "...",
      "demand": "...",
      "resolution": "...",
      "stage": "...",
      "essence": "..."
    }
    ```
    из `state.matchingText` (с сохранением `dictionaryVersion`).
  - Сохранение полного массива `actions` (тип, заголовок, порядок, отметки `done`, состояние `open`, а также все специфичные поля: `time`, `script`, `text`, `points`, `reason`, `approval`, `target`, `taskNo`, `commentText`, `customText`).
  - Сохранение массива `themes` в текущем порядке сортировки оператора.
  - Сохранение всех полей контекста клиента (`clientContext`), вердикта (`verdict`), `outcome` (`check`, `reply`, `comment`), `chrono`, `status`, `whatWorked`, `qcComments`.
- Обновление `sanitizeCaseCard()` / `redactPii()`:
  - Очистка PII не только в базовых полях, но и внутри текстовых полей объектов `actions` (скрипт звонка, текст чата, комментарий, текст задач) и `matching.essence`.

### 3.3. Совместимость со скриптом `process_cases.py`
- Проверка по коду `process_cases.py`:
  - Требование `ticket` или `order` соблюдается (`card.ticket || card.order`).
  - Все поля, используемые `process_cases.py` для `manifest.json` (`id`, `title`, `date`, `ticket`, `order`, `clientId`, `themes`, `problem`, `demand`, `whatWorked`, `qcComments`, `verdict`, `themesVersion`), присутствуют на верхнем уровне JSON.
  - Поля `actions`, `matching`, `clientContext` сохраняются без изменений в целевом файле `cases/<filename>.json`.

### 3.4. Загрузка старых и новых кейсов (`js/cases.js` & `js/case-loader.js`)
- Обновление `loadCaseIntoForm(card, file)`:
  - **Если `card.actions` есть (новый формат)**: загружаем массив `actions` как есть, восстанавливая все поля и порядок.
  - **Если `card.actions` отсутствует (старый формат)**:
    - Создаём базовый список действий (`getDefaultActions()`).
    - Инициализируем `chat.text` из `card.outcome?.reply`.
    - Инициализируем `comment.commentText` из `card.outcome?.comment`.
  - **Если `card.matching` есть (новый формат)**:
    - Преобразуем объект в строки `ключ: значение` и записываем в `state.matchingText` и элемент `#matching-text`.
    - Восстанавливаем `card.dictionaryVersion`.
  - **Если `card.matching` отсутствует (старый формат)**:
    - `state.matchingText = ""`, поле на шаге 4 готово для ввода.

### 3.5. Предпросмотр карточки (`js/steps/step5.js`)
- Обновление `renderPreview()`:
  - Удаление отображения старого `summary` и `problemMatch`.
  - Добавление отображения нового блока matching: красивый вывод параметров (`problemType`, `blockers`, `fault`, `demand`, `resolution`, `stage`, `essence`) с бейджем версии словаря.
  - Подробный предпросмотр чеклиста исполнения.

## 4. План верификации

1. **Проверка разметки**: отсутствие `case-summary` на шаге 5, чистый интерфейс.
2. **Проверка сохранения**:
   - Заполнение формы, генерация JSON через `buildCaseCard()`.
   - Проверка структуры: присутствие `actions`, `matching` (в виде объекта), `clientContext`, `themes` в правильном порядке.

   - Проверка успешного прохождения валидации и сборки манифеста.
4. **Проверка загрузки старого формата**:
   - Загрузка приложенного файла `2026-10-07_753683844.json`.
   - Проверка переноса текстов `outcome.reply` и `outcome.comment` в карточки шага 4.
